# Instance-local MXFP8 exclusion patch

Last updated: 09/18/2026

## Status and scope

This is a standalone helper and CPU regression suite. It is **not wired into
rollout startup** and does not add CUDA MXFP8 rollout support to `main`. The
MXFP8 feature branch must integrate it explicitly before it can fix a live run.

vLLM 0.24's `ModelOptQuantConfigBase.is_layer_excluded()` includes a legacy
substring fallback. A router exclusion such as `model.layers.0.mlp.gate` also
matches the dense SwiGLU `model.layers.0.mlp.gate_up_proj`. Both HF projections
(`gate_proj` and `up_proj`) can consequently remain unquantized in rollout.
The upstream comment about ModelOpt 0.39 is not a runtime version guard.

`verl.utils.vllm.mxfp8_exclusion_patch.apply_mxfp8_exclusion_patch` installs a
replacement matcher on **one explicitly opted-in ModelOpt MXFP8 config instance**.
It does not modify ModelOpt classes or `get_quant_method`. Unmarked checkpoint
configs, other config instances, and other quantization backends are untouched.

## Integration contract for the MXFP8 feature branch

1. Only when verl itself generates an online MXFP8 HF quantization config, add
   `_verl_exact_mxfp8_exclusions: true`. Do not add this marker to loaded user or
   checkpoint configs. Keep all real router/high-precision exclusions; this helper
   fixes matching, not router discovery across model architectures.
2. Pass the raw HF config (including the marker) across process boundaries.
   Unknown fields are not assumed to survive inside vLLM's parsed quant config:
   the helper reads provenance from the raw HF config supplied by the caller.
3. In **each model-building process**, after config parsing/name mapping and
   before constructing linear/MoE layers, call the helper on the corresponding
   parsed config instance. Reapply in the receiving process after deserialization;
   do not use a serialized bound method as the installation mechanism. A driver-
   only patch or a post-refit call is insufficient.

```python
from verl.utils.vllm.mxfp8_exclusion_patch import (
    VERL_EXACT_MXFP8_EXCLUSIONS,
    apply_mxfp8_exclusion_patch,
)

# Future integration: ONLY the config generated by verl for online MXFP8.
hf_quant_config = {
    "quant_method": "mxfp8",
    "ignored_layers": ["model.layers.0.mlp.gate", "lm_head", "model.embed_tokens"],
    VERL_EXACT_MXFP8_EXCLUSIONS: True,
}

# In the actual model-building worker, BEFORE model construction:
apply_mxfp8_exclusion_patch(
    vllm_config.quant_config,
    hf_quant_config=hf_quant_config,
)
```

The example lists one layer for brevity; production integration must supply its
complete policy and the actual raw config corresponding to the parsed instance.
The marker is an explicit opt-in, not authentication or automatic proof of origin.
The caller owns provenance. Repeated installation is a no-op; invalid marked
configs raise instead of silently leaving the legacy matcher active.

## Matching contract

- Ordinary module names match exactly, not by substring or implicit descendants.
  Use an explicit glob such as `model.layers.0.mlp.*` to exclude descendants.
- Case-sensitive `fnmatch`-style globs are supported, not `re:` expressions.
- Patterns are evaluated against the fused runtime name and its HF shard names.
  Literal matches are passed to vLLM's `is_layer_skipped()` so all-or-none shard
  validation is preserved (including mixed exact/glob exclusions).
- An explicit exclusion of the fused module applies to the whole module.
- The upstream helper's specialized fused-expert-group handling is retained;
  this is not a new per-expert precision policy.
- Current `exclude_modules` and `packed_modules_mapping` are read on each call;
  the helper does not cache exclusion decisions or change the weight-sync cache.

## Validation

```bash
python -m pytest tests/utils/test_mxfp8_exclusion_patch_on_cpu.py -q
```

CPU tests use lightweight vLLM doubles and check the 28-layer/56-HF-parameter
collision, router preservation, instance isolation, legacy checkpoint behavior,
explicit opt-in, invalid inputs, fused shards, globs, and idempotence. They do not
establish GPU kernel correctness or that the feature branch installed the helper
in the correct worker.

Before deployment, validate against the installed vLLM matcher and then rebuild
the engine: check `gate_up_proj.quant_method`, weight dtype and scales on B200,
check initial and post-training refits, and ensure engine recheck no longer finds
the 56 gate/up discrepancies. Include a real MoE router regression and retain the
refit self-check. Updating only an already-built model's config cannot rebuild
its BF16 layers as MXFP8 layers.
