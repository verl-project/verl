# Qwen3.6-35B-A3B multi-teacher OPD on reasoning_gym (Megatron EP4, one-step async)

`../run_qwen3_6_35b_mopd_megatron.sh` distills Qwen3.6-35B-A3B from two frozen GRPO teachers, one per
reasoning_gym task, on 8 GPUs:

| Role | GPUs | Engine |
|---|---|---|
| Student trainer | 4 | Megatron, EP4, no TP/PP/CP, no offload, precision-aware Adam (bf16 moments) |
| Student rollout | 2 | two vLLM TP1 engines with MTP speculative decoding (2 draft tokens) |
| caesar_cipher teacher | 1 | vLLM TP1 |
| simple_geometry teacher | 1 | vLLM TP1 |

Training is `trainer.v1.trainer_mode=separate_async` with `parameter_sync_step=1` and
`rollout.weight_sync_pause_mode=wait`: batch k+1 generates while batch k trains, and the weight update
waits for batch k+1's in-flight requests to finish, so every response is generated by one policy
version and is exactly one version behind the trainer. The objective is the `k1` estimator as a
per-token policy-gradient reward (`use_policy_gradient=True`), no task reward, token-mean loss,
rollout log-probs as old log-probs (`rollout_correction.bypass_mode=True`).

This is the same workload as Miles' `mopd_reasoning_gym` example (radixark/miles#4493, `gb300-async`
layout with `--mtp-spec-decode`): same models, prompts, layout, batch, sampling, objective and eval.

The teacher cards report held-out avg@4 of 73.3% (caesar_cipher) and 99.8% (simple_geometry).

**Data**: `prepare_data.py` generates the prompts with reasoning_gym 0.1.25: 10,000 train prompts per
task (seed 20000), mixed and shuffled, and 128 held-out prompts per task (seed 10000), with
reasoning_gym's default system prompt and thinking on. The output is row-for-row identical to Miles'
`prepare_data.py` output converted to verl's schema.

```bash
pip install reasoning_gym==0.1.25
python examples/on_policy_distillation_trainer/qwen3_6_35b_mopd/prepare_data.py \
    --out ~/data/mopd_reasoning_gym --tokenizer $MODELS/student
```

`reward.py` scores each response with its task's reasoning_gym `score_answer` on the answer after
`</think>` (exact match), the teachers' own reward. It feeds only the accuracy metrics; the
objective does not use it.

**Launch** (one 8-GPU node, or start a 2 x 4 GPU Ray cluster and run on the head node):

```bash
STUDENT_MODEL=$MODELS/student CAESAR_TEACHER_MODEL=$MODELS/caesar_cipher \
GEOMETRY_TEACHER_MODEL=$MODELS/simple_geometry DATA_DIR=~/data/mopd_reasoning_gym \
bash examples/on_policy_distillation_trainer/run_qwen3_6_35b_mopd_megatron.sh
```

Tested stack: vLLM nightly `8e2beaa3bf`, torch 2.14, transformers 5.20, Transformer Engine 2.16.0,
Megatron-Core 0.19.2, Megatron-Bridge 0.6.2, flash-attn 2.8.3 (built for sm_100 / sm_103).

steps: avg@4 at temperature 1.0 on the 128 + 128 held-out prompts. Step time excludes eval.

|---|---|---|---|
| Median step | 120.9 s | 121.6 s | 173 s |
| Sum of 20 steps | 2634 s | 2666 s | |
| Training GPU-hours (8 x step time) | 5.85 | 5.92 | 7.9 |
| One eval (1,024 rollouts) | 440 s | 397 s | 5-7 min |
| caesar_cipher avg@4, step 0 / 10 / 20 | 28.9 / 75.0 / 75.6 % | 26.0 / 74.6 / 76.0 % | final 78.5 % |
| simple_geometry avg@4, step 0 / 10 / 20 | 52.3 / 100 / 99.8 % | 51.2 / 99.2 / 99.8 % | final 99.6 % |

One seed per setting; the eval's standard error is about 2-3 points. Both runs passed the teachers on
caesar_cipher (73.3%) by step 10 and matched them on simple_geometry.

Per step (median): `update_actor` 41 s; `update_weights` 78 s, which is mostly the wait for the next
batch's longest response (every step has at least one response at the 30,720-token cap) plus the NCCL
transfer. The step is rollout-bound: the trainer waits on the slowest sequence of the next batch.

## Why these settings

All numbers below are from this workload (Qwen3.6-35B-A3B, 128 prompts, 30,720 max tokens).

**MTP speculative decoding on the rollout.** A step waits for its longest sequence, so single-sequence
decode speed matters more than throughput. One engine's share of a step (64 requests at fixed output
lengths sampled from real rollouts, mean 7.9k, max 30.7k tokens), one GPU:

| Rollout engine (one GPU) | GB300 batch time | GB300 single-seq tok/s | GB200 batch time | acceptance length |
|---|---|---|---|---|
| vLLM, no MTP | 202.7 s | 307 | 196.8 s | |
| vLLM, MTP 2 | 100.0 s | 572 | 110.0 s | 2.54 |
| vLLM, MTP 4 | 88.3 s | 828 | 105.0 s | 3.33 |
| SGLang 0.5.23, EAGLE 2 steps / 3 draft tokens (Miles' flags) | 122.8 s | 471 | | |

The recipe defaults to 2 draft tokens to match Miles; `NUM_SPECULATIVE_TOKENS=4` is about 12% faster on
GB300 and 5% on GB200 (in a 20-step GB200 run: 90-110 s per step). Deeper drafts (6, or depth chosen
by batch size) were slower.

**MTP on the rollout side only, with `load_format=auto`.** `model.mtp.enable` turns off the fused
log-prob kernels in the trainer, and without them a 30,720-token response materializes a 28 GiB fp32
logits copy. `rollout.mtp` enables the drafter in vLLM without adding an MTP layer to the trained model.
The drafter is then never synced from the trainer, so the rollout must load it from the checkpoint:
with the default `load_format=dummy` it stays random, and MTP made rollout 1.7x slower in our runs. The
drafter is frozen; generation time did not drift up over 20 steps.

**`weight_sync_pause_mode=wait`.** With the default `abort`, a sync aborts in-flight requests and the
agent loop resumes them under the new weights. Steps were faster (about 57 s with the FSDP trainer on
the same layout), but long responses kept getting aborted and finished in later batches, so each
batch was biased to short responses (mean length 4-6k against 8-9k). `wait` keeps the batch
unbiased; this is Miles' one-step overlap.

**Precision-aware Adam, fused log-probs, THD dynamic batching on the Megatron trainer.** EP4 on 4 GPUs
leaves expert data-parallel size 1, so the distributed optimizer cannot shard expert states.

| Trainer (GB200, Miles layout) | train s / step | step s |
|---|---|---|
| BSHD, micro batch 1, CPU Adam | 162-195 | 171-204 |
| THD + fused log-probs, CPU Adam | 232 | 239 |
| THD + fused log-probs + precision-aware Adam (bf16 moments) | 43-57 | 92-99 (MTP 4) |

fp32 Adam moments on GPU run out of memory (164 GiB). FSDP2 on the same 4 GPUs trains in about 39 s,
similar to Megatron with these flags.

**Rollout log-probs as old log-probs (`bypass_mode=True`).** With one mini-batch and one epoch per step,
the recomputed old log-probs only anchor the PPO ratio at 1; bypass skips that pass (9 s per step in the
synchronous setup) and makes the ratio train/rollout. The train-rollout mismatch is `ppo_kl` about 0.001,
and about 0.2% of tokens are clipped.

**Rollout and teacher parallelism.** The bf16 student is 70 GB and fits one GPU. The recipe runs two
TP1 rollout engines to match Miles; one TP2 engine on the same 2 GPUs (`ROLLOUT_TP=2`) was faster in our
runs with MTP 4: 92.9 s per step on GB300 against 105.7 s for 2 x TP1 on GB200 (Megatron trainer), and
94.8 s against 111.7 s on GB200 with the FSDP trainer, because the step waits on the single longest
sequence. Teachers score a step's batch in seconds (about 5 s on one GPU for 64 trajectories, 400k
tokens) and sit idle 72-88% of their scoring window, so one GPU each is enough. They run with CUDA
graphs (`enforce_eager=False`) and 32k batched tokens.

How the setup got here, from the original synchronous recipe (16 GB200, FSDP2 with offload, colocated
vLLM 4 x TP2 without MTP, teachers TP4 eager), median of steps 2-20:

| Setup | GPUs | Step s | GPU-s per step |
|---|---|---|---|
| Original synchronous recipe | 16 | 169.0 | 2704 |
| + MTP 4 (real drafter weights), teachers TP2 with CUDA graphs, bypass | 12 | 95.6 | 1147 |
| + teachers TP1, no FSDP offload, colocated weight-sync patches (not in this PR) | 10 | 89.3 | 893 |
| One-step async (`wait`), Miles layout, FSDP2 trainer, 1 x TP2 rollout, MTP 4 | 8 | 95.2 | 762 |
| Same with Megatron EP4 trainer, on GB300 | 8 | 92.9 | 743 |
| Megatron EP4, 2 x TP1 rollout, MTP 4 | 8 | 105.7 | 846 |
| This recipe: 2 x TP1 rollout, MTP 2 (Miles' setting) | 8 | 120.9 (GB200) / 121.6 (GB300) | 967 / 973 |

GB200 unless noted.

The synchronous runs reached 79.2% / 99.6% at step 20.

## Notes

- On GB300 (sm_103), Transformer Engine 2.16 allows FlashAttention 2 for head_dim > 192 only on
  sm80/90/100/120 and cuDNN has no fused backend for this shape, so TE falls back to unfused attention
  and runs out of memory (57.7 GiB). Adding `(10, 3)` to that list in
  `transformer_engine/pytorch/attention/dot_product_attention/utils.py` (with a flash-attn build that
  includes sm_103) fixes it. Keep NCCL MNNVL enabled on GB200/GB300 NVL racks: with it off, the first
  weight sync took 17.9 s instead of 9.2 s.
- Each eval shares the 2 rollout GPUs with the unfinished training batch, so it takes about 7 min.
- Startup loads three 70 GB checkpoints; on a network file system, copy them to local disk or
  `/dev/shm` first.
